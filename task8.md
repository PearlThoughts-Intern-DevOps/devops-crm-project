2. Introduction to Observability

Observability is the ability to understand the internal state of an application or infrastructure by analysing the data it produces.

In cloud environments, applications contain multiple services, servers, databases, containers, APIs, and networking components. When a problem occurs, observability helps identify:
- What happened
- When it happened
- Which component caused the issue
- How the issue affected users
- How the issue can be resolved
- How to prevent the issue in the future

Observability is mainly based on three important data types:
1. Metrics
2. Logs
3. Traces

---

3. Three Pillars of Observability

3.1 Metrics
Metrics are numerical measurements collected over time.

Examples:
- CPU utilisation
- Memory usage
- Request count
- Error count
- Network traffic
- Disk usage
- Application response time
- Number of active users

Metrics help identify the overall health and performance of a system:
- High CPU usage may indicate heavy processing.
- Increased error count may indicate an application problem.
- High response time may indicate a slow service or database.

3.2 Logs
Logs are records of events generated by applications, operating systems, and services.

Examples:
- Application startup messages
- Login attempts
- API errors
- Authentication failures
- Database connection errors
- Container output
- System warnings

Logs provide detailed information about what happened inside a system.

3.3 Traces
Traces show the complete journey of a request through different services.

For example:
1. A user sends a request.
2. The request reaches an API.
3. The API calls an authentication service.
4. The authentication service calls a database.
5. The response is returned to the user.

Tracing helps identify which part of the request is slow or failing.

4. Why Observability Is Important

Observability is important because it helps teams:
- Detect issues quickly
- Reduce application downtime
- Troubleshoot errors
- Understand application performance
- Monitor infrastructure health
- Improve user experience
- Identify security-related activities
- Maintain compliance
- Analyse historical events
- Create alerts for abnormal behaviour
- Understand dependencies between services

Without observability, engineers may need to guess the cause of an issue.

5. Amazon CloudWatch

5.1 Overview
Amazon CloudWatch is an AWS monitoring and observability service. It collects and monitors metrics, logs, events, and other operational data from AWS resources and applications. CloudWatch helps users understand the performance and health of their infrastructure and applications.

5.2 Purpose of CloudWatch
CloudWatch is mainly used to:
- Monitor AWS resources
- Collect application logs
- Create alarms
- Track performance
- Detect abnormal behaviour
- Monitor resource utilisation
- Automate responses to events
- Create dashboards
- Analyse historical metrics

5.3 Main Features

Metrics
CloudWatch collects metrics from many AWS services.  
Examples:
- EC2 CPU utilisation
- EC2 network traffic
- Application Load Balancer request count
- RDS database connections
- Lambda invocation count
- Lambda error count

Logs
CloudWatch Logs stores and displays log data. Logs can be collected from:
- Applications
- EC2 instances
- Lambda functions
- Containers
- AWS services
- Custom applications

Logs are organised using:
- Log groups
- Log streams
- Log events

Alarms
CloudWatch alarms monitor metrics and trigger actions when a condition is met.  
Examples:
- If CPU usage remains above 80%, trigger an alarm.
- If an application error count increases, send a notification.
- If a resource becomes unhealthy, start an automated response.

Dashboards
CloudWatch dashboards display multiple metrics in one place. A dashboard can contain:
- CPU usage
- Memory usage
- Request count
- Error count
- Network traffic
- Application latency

Dashboards help teams monitor systems more easily.

Events and EventBridge Integration
CloudWatch can work with Amazon EventBridge to detect events and trigger actions.  
Examples:
- An EC2 instance changes state.
- A new AWS resource is created.
- A scheduled event occurs.
- A security-related event is detected.

5.4 How CloudWatch Works
The basic working process is:
1. AWS resources generate operational data.
2. CloudWatch collects metrics, logs, and events.
3. The data is stored and organised.
4. Users view the data through the AWS Console.
5. Alarms can be configured based on specific conditions.
6. Notifications or automated actions can be triggered.

5.5 CloudWatch Metrics
CloudWatch metrics contain:
- Metric name
- Namespace
- Timestamp
- Value
- Unit
- Dimensions

A namespace groups related metrics (e.g., AWS/EC2, AWS/Lambda, AWS/RDS).  
Dimensions provide additional information about the metric (e.g., an EC2 CPU metric may contain the instance ID as a dimension).

5.6 CloudWatch Logs
CloudWatch Logs uses the following structure:
- Log Group: A collection of related log streams (e.g., /aws/lambda/application-function).
- Log Stream: A sequence of log events from one source.
- Log Event: An individual log message with a timestamp.

5.7 CloudWatch Logs Insights
CloudWatch Logs Insights allows users to query and analyse log data. It can be used to:
- Search for errors
- Filter specific messages
- Count requests
- Analyse response times
- Find repeated failures
- Identify patterns

Example query:
```sql
fields @timestamp, @message 
| filter @message like /ERROR/ 
| sort @timestamp desc 
| limit 20
```
This query displays recent log messages containing the word ERROR.

5.8 CloudWatch Alarms
A CloudWatch alarm contains:
- Metric
- Threshold
- Evaluation period
- Comparison condition
- Alarm action

Example:
- Metric: CPUUtilization
- Condition: Greater than 80%
- Period: 5 minutes
- Action: Send notification

Alarm states include:
- OK
- ALARM
- INSUFFICIENT_DATA

5.9 CloudWatch Agent
The CloudWatch Agent collects additional system-level metrics and logs. It can collect:
- Memory usage
- Disk usage
- Disk space
- Process information
- Custom application logs

Some operating system metrics are not available by default. In such cases, the CloudWatch Agent can be installed and configured.

5.10 Real-World Use Cases
CloudWatch can be used for:
- Monitoring EC2 instances
- Monitoring Lambda functions
- Tracking API performance
- Monitoring databases
- Creating infrastructure dashboards
- Detecting high CPU usage
- Sending alerts for application failures
- Collecting server logs
- Monitoring production environments

5.11 Practical Understanding
During the exploration of CloudWatch, the following areas were studied:
- CloudWatch dashboard
- Metrics section
- Logs section
- Alarms section
- Event monitoring
- Metric namespaces
- Log groups and log streams
- Basic alarm configuration

CloudWatch is useful for observing the health and performance of AWS resources from a central location.

6. AWS CloudTrail

6.1 Overview
AWS CloudTrail is an AWS service used to record and monitor API activity and account actions. It provides a history of actions performed in an AWS account.

CloudTrail helps answer:
- Who performed an action?
- What action was performed?
- When was it performed?
- Which resource was affected?
- From where was the request made?

6.2 Purpose of CloudTrail
CloudTrail is mainly used for:
- Auditing AWS activity
- Security investigation
- Compliance
- Tracking configuration changes
- Monitoring account activity
- Identifying unauthorised actions
- Troubleshooting resource changes

6.3 Main Features

Event History
CloudTrail provides recent management events in the AWS Console.  
Examples:
- EC2 instance started
- Security group modified
- IAM policy changed
- S3 bucket created
- User logged in
- Resource deleted

Trails
A trail delivers CloudTrail events to a destination such as Amazon S3. Trails can be configured to collect and retain activity for longer periods.

Management Events
Management events record control-plane operations.  
Examples:
- Creating an EC2 instance
- Updating an IAM policy
- Creating a VPC
- Deleting a security group

Data Events
Data events record operations performed on resources.  
Examples:
- Reading an object from an S3 bucket
- Writing an object to an S3 bucket
- Invoking a Lambda function

Data events can generate a large amount of information, so they should be configured carefully.

Insights Events
CloudTrail Insights helps identify unusual API activity. It can detect changes such as:
- Sudden increase in API calls
- Unusual resource creation
- Abnormal usage patterns

6.4 How CloudTrail Works
The basic working process is:
1. A user or AWS service performs an action.
2. The action generates an API event.
3. CloudTrail records the event.
4. The event contains information about the request.
5. Users view the event history or store events in Amazon S3.
6. The events can be analysed for auditing and security.

6.5 Information in a CloudTrail Event
A CloudTrail event may contain:
- Event name
- Event time
- AWS service
- Username or principal
- Source IP address
- AWS region
- Resource name
- Request parameters
- Response information

6.6 Example CloudTrail Activities
Examples of activities recorded by CloudTrail include:
- Starting an EC2 instance
- Stopping an EC2 instance
- Creating an IAM user
- Changing a security group
- Updating an S3 bucket policy
- Creating a CloudWatch alarm
- Modifying a network configuration

6.7 CloudTrail and Security
CloudTrail helps security teams investigate:
- Unauthorised access
- Unexpected resource deletion
- IAM permission changes
- Unusual login activity
- Changes to security groups
- Changes to encryption settings

CloudTrail should be enabled and configured properly for important AWS accounts.

6.8 CloudTrail and Compliance
CloudTrail supports compliance by maintaining a record of account activity. It helps organisations demonstrate:
- Who changed a resource
- When a change occurred
- Which resource was modified
- Whether administrative activity was recorded

6.9 CloudTrail with Other AWS Services
CloudTrail can work with:
- Amazon S3 for long-term storage
- CloudWatch for monitoring
- Amazon EventBridge for event-driven actions
- AWS Security Hub for security findings
- Amazon Athena for querying stored logs

6.10 Real-World Use Cases
CloudTrail can be used for:
- Auditing administrator activity
- Investigating security incidents
- Tracking infrastructure changes
- Monitoring IAM actions
- Supporting compliance requirements
- Finding the source of unexpected changes
- Reviewing account activity

6.11 Practical Understanding
During the exploration of CloudTrail, the following areas were studied:
- Event history
- Management events
- Event details
- User identity information
- Event source
- Event name
- Resource information
- Trail configuration

CloudTrail is mainly focused on who did what in the AWS account.

7. AWS X-Ray

7.1 Overview
AWS X-Ray is a distributed tracing service. It helps developers analyse requests as they travel through applications and services.

X-Ray is useful for applications that contain multiple components such as:
- APIs
- Lambda functions
- Containers
- Databases
- Microservices
- External services

7.2 Purpose of X-Ray
X-Ray helps to:
- Identify slow requests
- Find service errors
- Understand service dependencies
- Analyse application latency
- Troubleshoot distributed applications
- Identify bottlenecks
- Understand request flow

7.3 Main Features

Traces
A trace represents the complete path of a request through an application.

Segments
A segment contains information about work performed by an application component (e.g., API processing, Lambda execution, Database operation).

Subsegments
Subsegments provide more detailed information inside a segment (e.g., Database query, HTTP request, AWS SDK call).

Service Map
The service map shows the relationship between application components. It helps identify:
- Connected services
- Request flow
- Error locations
- High-latency services

Annotations
Annotations are indexed key-value pairs that can be used for filtering traces (e.g., environment = production, userType = admin).

Metadata
Metadata contains additional information attached to a trace. Metadata is useful for debugging but is not primarily used for filtering.

7.4 How X-Ray Works
The basic working process is:
1. An application receives a request.
2. X-Ray instrumentation records the request.
3. The request is divided into segments and subsegments.
4. Trace data is sent to X-Ray.
5. X-Ray processes and stores the trace data.
6. Developers view traces and service maps.
7. Slow or failed components are identified.

7.5 X-Ray Trace Information
A trace may include:
- Request URL
- Request method
- Response status
- Request duration
- Service name
- Error information
- Database calls
- External API calls
- AWS service calls

7.6 X-Ray Sampling
X-Ray uses sampling to control the amount of trace data collected. Sampling helps reduce:
- Storage usage
- Processing overhead
- Cost
- Unnecessary trace data

Sampling rules can be configured based on application requirements.

7.7 X-Ray and Microservices
In a microservices architecture, a request may pass through multiple services. Without tracing, it can be difficult to identify which service caused a delay.

X-Ray helps show:
- The complete request path
- Time spent in each service
- Failed service calls
- Database latency
- External API latency

7.8 Example Request Flow

```text
Client ──► API Gateway ──► Lambda Function ──► Database ──► Response
```

X-Ray can help measure the time spent at each stage.

7.9 Important Limitation
X-Ray does not automatically provide detailed traces for every application. The application or service must support X-Ray integration or instrumentation.

Without instrumentation:
- Trace data may not be available.
- Service-level request details may not be visible.
- Application code may need configuration changes.

7.10 Real-World Use Cases
X-Ray can be used for:
- Debugging microservices
- Monitoring serverless applications
- Finding slow database queries
- Analysing API latency
- Tracking distributed requests
- Investigating application errors
- Understanding service dependencies

7.11 Practical Understanding
During the exploration of X-Ray, the following concepts were studied:
- Distributed tracing
- Trace
- Segment
- Subsegment
- Service map
- Sampling
- Annotations
- Metadata
- Instrumentation

X-Ray is mainly focused on how a request travels through an application.

8. AWS Distro for OpenTelemetry

8.1 Overview
AWS Distro for OpenTelemetry, also called ADOT, is an AWS-supported distribution of OpenTelemetry.

OpenTelemetry is an open-source observability framework used to collect:
- Metrics
- Logs
- Traces

ADOT helps applications send observability data to supported monitoring and tracing backends.

8.2 Purpose of ADOT
ADOT is used to:
- Collect telemetry data
- Standardise observability data
- Instrument applications
- Export data to monitoring systems
- Reduce dependency on one observability vendor
- Support multiple programming languages
- Monitor distributed applications

8.3 Main Features

OpenTelemetry Compatibility
ADOT follows OpenTelemetry standards, making it easier to use common telemetry formats and tools.

Application Instrumentation
Applications can be instrumented to generate telemetry data, collecting:
- Request duration
- Error information
- Service calls
- Database operations
- Application metrics

Collector
The OpenTelemetry Collector receives, processes, and exports telemetry data. The collector can:
- Receive telemetry data
- Transform data
- Filter data
- Batch data
- Export data to supported destinations

Multiple Exporters
ADOT can send data to different backends depending on the configuration:
- AWS X-Ray
- Amazon CloudWatch
- Amazon Managed Service for Prometheus
- Other OpenTelemetry-compatible systems

8.4 How ADOT Works
The basic working process is:
1. An application generates telemetry data.
2. OpenTelemetry instrumentation collects the data.
3. The data is sent to the ADOT Collector.
4. The collector processes the data.
5. The collector exports the data to a backend.
6. The backend displays and analyses the data.

8.5 ADOT Collector Components
The collector commonly contains:
- Receivers: Accept telemetry data.
- Processors: Modify or prepare the data.
- Exporters: Send the data to a destination.
- Service Pipelines: Define how telemetry data moves through the collector.

8.6 Example ADOT Flow

```text
Application 
   │
   ▼
OpenTelemetry Instrumentation 
   │
   ▼
ADOT Collector 
   ├───► CloudWatch
   ├───► X-Ray
   └───► Prometheus
```

8.7 ADOT and Vendor Neutrality
ADOT supports a standardised observability approach, helping organisations avoid tightly coupling application code with one monitoring platform. The same application telemetry can be exported to different compatible systems.

8.8 ADOT Supported Environments
ADOT can be used in environments such as:
- Amazon EC2
- Amazon ECS
- Amazon EKS
- AWS Lambda
- Kubernetes
- Container-based applications
- Cloud-native applications

8.9 Important Considerations
ADOT requires proper configuration across:
- Application instrumentation
- Collector configuration
- Receiver configuration
- Processor configuration
- Exporter configuration
- IAM permissions
- Network access
- Backend configuration

8.10 Real-World Use Cases
ADOT can be used for:
- Instrumenting microservices
- Collecting application traces
- Collecting custom metrics
- Exporting telemetry to AWS services
- Monitoring Kubernetes applications
- Standardising observability across teams
- Connecting applications to multiple backends

8.11 Practical Understanding
During the exploration of ADOT, the following concepts were studied:
- OpenTelemetry
- Instrumentation
- Collector
- Receivers
- Processors
- Exporters
- Pipelines
- Vendor-neutral telemetry

ADOT is mainly focused on collecting and exporting observability data using open standards.

9. Amazon Managed Service for Prometheus

9.1 Overview
Amazon Managed Service for Prometheus, also called AMP, is a fully managed monitoring service compatible with Prometheus.

Prometheus is an open-source monitoring and alerting system commonly used for cloud-native applications and Kubernetes environments. AMP removes the need to manage Prometheus servers manually.

9.2 Purpose of AMP
AMP is used to:
- Collect and store metrics
- Monitor Kubernetes workloads
- Query Prometheus metrics
- Create alerts
- Scale monitoring infrastructure
- Reduce operational overhead
- Support cloud-native monitoring

9.3 Main Features

Prometheus Compatibility
AMP supports Prometheus-compatible metrics and queries, allowing existing Prometheus knowledge and tools to be used.

Managed Infrastructure
AWS manages the underlying infrastructure so users do not need to manually maintain Prometheus servers.

Scalable Metrics Storage
AMP is designed to store and query metrics at scale, making it suitable for large monitoring environments.

PromQL Support
PromQL is the Prometheus Query Language used to query and analyse metrics.  
Example:
```promql
up
```
This query checks whether monitored targets are available.

Alerting
AMP can be used with alerting configurations to detect metric conditions:
- High CPU usage
- Pod restart count
- High memory usage
- Service availability issues

9.4 How AMP Works
The basic working process is:
1. Applications or exporters generate metrics.
2. Prometheus-compatible agents collect the metrics.
3. Metrics are sent to an AMP workspace.
4. AMP stores the metrics.
5. Users query the metrics using PromQL.
6. Dashboards and alerts are created using supported tools.

9.5 AMP Workspace
An AMP workspace is a logical environment used to store and manage Prometheus metrics. A workspace provides:
- A remote write endpoint
- A query endpoint
- Access control
- Metric storage
- Integration with monitoring tools

9.6 Prometheus Metrics
Prometheus metrics are usually represented as time-series data. A metric may contain:
- Metric name
- Value
- Timestamp
- Labels

Example:
```text
http_requests_total{method="GET",status="200"} 150
```
Labels provide additional information about the metric.

9.7 PromQL Examples

Check target availability:
```promql
up
```

Calculate request rate:
```promql
rate(http_requests_total[5m])
```

Find high CPU usage:
```promql
100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]) * 100)
```

These queries are examples of how PromQL can be used to analyse metrics.

9.8 AMP and Kubernetes
AMP is commonly used with Kubernetes monitoring. It can collect metrics related to:
- Nodes
- Pods
- Containers
- Deployments
- Services
- CPU usage
- Memory usage
- Restart counts

9.9 AMP Security
AMP access can be controlled using AWS IAM. Important security areas include:
- Workspace permissions
- Authentication
- Data access
- Network configuration
- Query access
- Remote write permissions

9.10 Real-World Use Cases
AMP can be used for:
- Kubernetes monitoring
- Container monitoring
- Application metrics
- Infrastructure metrics
- Prometheus-compatible dashboards
- Alerting
- Large-scale time-series monitoring

9.11 Practical Understanding
During the exploration of AMP, the following concepts were studied:
- Prometheus
- PromQL
- Time-series metrics
- Labels
- Exporters
- Remote write
- AMP workspace
- Managed monitoring

AMP is mainly focused on storing and querying Prometheus-compatible metrics.

13. Difference Between CloudWatch and CloudTrail

CloudWatch and CloudTrail serve different purposes:

CloudWatch answers:
- How is the resource performing?
- Is CPU usage high?
- Are there application errors?
- Is the service healthy?
- Should an alarm be triggered?

CloudTrail answers:
- Who changed the resource?
- What API action was performed?
- When did the change happen?
- Which account or user performed the action?

CloudWatch focuses on performance and operational monitoring. CloudTrail focuses on activity tracking and auditing.

14. Difference Between X-Ray and ADOT

X-Ray: An AWS tracing service used to analyse request flow and application dependencies.  
ADOT: An OpenTelemetry-based collection and export framework that can collect telemetry and send it to supported backends, including X-Ray.

X-Ray is mainly used for tracing analysis, while ADOT is mainly used for telemetry collection and exporting.

CloudWatch can be used directly for monitoring, while AMG provides a more customisable dashboard experience across multiple data sources.

17. Difference Between CloudTrail and AWS Config

CloudTrail: Records actions performed in the AWS account (answers "Who performed the change?").  
AWS Config: Records the configuration state of resources (answers "What was the resource configuration before and after the change?").

Both services can be used together for auditing and troubleshooting.
