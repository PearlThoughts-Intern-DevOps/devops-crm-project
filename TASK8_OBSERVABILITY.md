# Task 8 – AWS Observability

## 1. Introduction

AWS Observability is the practice of collecting, monitoring, analyzing, and correlating telemetry data such as metrics, logs, traces, and events to understand the health and performance of applications and infrastructure.

AWS provides multiple observability services that help DevOps engineers monitor infrastructure, troubleshoot application issues, analyze logs, trace distributed requests, create dashboards, and detect operational problems.

The major AWS observability services and tools explored in this task are:

* Amazon CloudWatch
* CloudWatch Logs and Logs Insights
* CloudWatch Application Signals
* CloudWatch Synthetics
* CloudWatch Real User Monitoring (RUM)
* AWS X-Ray
* AWS CloudTrail
* AWS Distro for OpenTelemetry (ADOT)
* Amazon Managed Service for Prometheus
* Amazon Managed Grafana
* Amazon OpenSearch Service

---

## 2. Amazon CloudWatch

### Purpose

Amazon CloudWatch is the primary AWS monitoring and observability service. It provides visibility into AWS resources, applications, and infrastructure.

CloudWatch can collect and monitor:

* Metrics
* Logs
* Events
* Traces
* Application performance data

### Important Features

* Metrics and dashboards
* CloudWatch Logs
* CloudWatch Logs Insights
* Alarms
* Application monitoring
* Infrastructure monitoring
* Container Insights
* Lambda Insights
* Database Insights
* Network monitoring

### Example Usage

For an EC2 instance, CloudWatch can be used to monitor:

* CPU utilization
* Network traffic
* Disk-related metrics
* Status checks
* Application logs

An alarm can also be configured to notify or trigger an action when a metric crosses a threshold.

### What I Learned

CloudWatch provides a centralized place to monitor AWS resources and applications. It is one of the most important services for day-to-day AWS operations.

---

## 3. CloudWatch Logs and Logs Insights

### Purpose

CloudWatch Logs stores logs generated by applications, AWS services, and infrastructure.

Logs Insights allows engineers to search and analyze large amounts of log data interactively.

### Example Usage

Application logs from an EC2 server can be sent to CloudWatch Logs using the CloudWatch Agent.

Logs Insights can then be used to find:

* Errors
* HTTP status codes
* Failed requests
* Application exceptions
* Frequently occurring events

### What I Learned

Logs are useful for understanding what happened inside an application or server, especially when troubleshooting errors.

---

## 4. CloudWatch Application Signals

### Purpose

Application Signals provides Application Performance Monitoring (APM) capabilities for applications running on AWS.

It focuses on application-level health and automatically collects important metrics such as:

* Latency
* Availability
* Error rate
* Request rate

It can also show relationships between services and dependencies through an Application Map.

### Example Usage

For a microservices application, Application Signals can help identify:

* Which service is slow
* Which service has a high error rate
* Which dependency is causing problems
* Whether application reliability objectives are being met

### What I Learned

Application Signals is useful when infrastructure metrics alone are not enough. It provides visibility into application performance and service dependencies.

---

## 5. CloudWatch Synthetics

### Purpose

CloudWatch Synthetics proactively tests applications and APIs using configurable canaries.

A canary simulates user actions or requests to check whether an application is working correctly.

### Example Usage

A canary can periodically:

1. Open a website.
2. Send an API request.
3. Verify the response.
4. Measure response time.
5. Generate an alert if the test fails.

### What I Learned

Synthetics can detect availability or performance problems before real users report them.

---

## 6. CloudWatch Real User Monitoring (RUM)

### Purpose

CloudWatch RUM collects performance information from real users accessing a web application.

It helps developers understand the actual user experience.

### It can provide information about:

* Page load performance
* Client-side errors
* User sessions
* Browser-related performance
* Application latency

### What I Learned

RUM provides visibility from the user's perspective, while CloudWatch infrastructure metrics show what is happening on the backend.

---

## 7. AWS X-Ray

### Purpose

AWS X-Ray is used for distributed tracing and application troubleshooting.

It tracks requests as they travel through different components of an application.

### Important Concepts

* Trace
* Segment
* Subsegment
* Annotations
* Sampling
* Service map

### Example

Consider:

```text
User
  |
  v
API
  |
  v
EC2 Application
  |
  +----> Database
  |
  +----> Another Service
```

X-Ray can help trace a request across these components and identify where latency or errors occur.

### What I Learned

X-Ray is particularly useful for distributed and microservices applications because it helps identify the exact part of the request path causing an issue.

AWS currently recommends moving toward OpenTelemetry-based instrumentation; the X-Ray SDK and daemon entered maintenance mode in February 2026.

## 8. AWS CloudTrail

### Purpose

AWS CloudTrail records API activity and account activity in AWS.

It is primarily used for:

* Auditing
* Security monitoring
* Compliance
* Investigating changes
* Tracking who performed an action

### Example

If an EC2 instance is terminated, CloudTrail can help identify:

* Which identity performed the action
* When it happened
* Which API call was made
* Relevant request details

### What I Learned

CloudWatch mainly helps answer:

> "How is my system performing?"

CloudTrail helps answer:

> "Who did what in my AWS account?"

Both are important for observability and operations.

## 9. AWS Distro for OpenTelemetry (ADOT)

### Purpose

AWS Distro for OpenTelemetry is an AWS-supported distribution of OpenTelemetry.

OpenTelemetry provides open-source standards and tools for collecting telemetry data.

ADOT can collect and send telemetry such as:

* Metrics
* Traces

to AWS monitoring services.

### Example

An application can be instrumented using OpenTelemetry and send telemetry to services such as:

* Amazon CloudWatch
* AWS X-Ray
* Amazon OpenSearch Service
* Amazon Managed Service for Prometheus

### What I Learned

OpenTelemetry provides a vendor-neutral approach to observability and reduces dependence on a single monitoring platform.

---

## 10. Amazon Managed Service for Prometheus

### Purpose

Amazon Managed Service for Prometheus is a fully managed, Prometheus-compatible monitoring service.

It is especially useful for containerized environments such as:

* Amazon EKS
* Amazon ECS
* Kubernetes environments

### Important Features

* Prometheus-compatible metrics
* PromQL querying
* Scalable metric storage
* Managed infrastructure
* Integration with Grafana and other AWS observability services

### Example

Kubernetes workloads can expose Prometheus metrics which can be collected and stored in Amazon Managed Service for Prometheus.

### What I Learned

Managed Prometheus is useful when teams want Prometheus-style monitoring without managing the underlying Prometheus infrastructure themselves.

Amazon Managed Grafana is a fully managed visualization and dashboard service.

It can visualize metrics, logs, and traces from multiple data sources.

### It can integrate with:

* Amazon CloudWatch

* Amazon OpenSearch Service

A DevOps team can create dashboards showing:

Grafana is mainly useful for visualization and creating centralized dashboards from multiple observability data sources.

### Purpose

Amazon OpenSearch Service provides search, analytics, and observability capabilities.

For observability, it can work with:

* Logs

# 13. Observability Signals

The three major observability signals are:

### Metrics

Metrics are numerical measurements over time.

Examples:

* CPU = 75%
* Memory = 60%
* Request rate = 500 requests/minute
* Latency = 200 ms

### Logs

Logs are records of events generated by applications and infrastructure.

Example:

```text
2026-09-03 15:20:10 ERROR Database connection failed
```

### Traces

Traces follow a request through different services.

Example:

```text
User Request
    |
    v
API Gateway
    |
    v
Application
    |
    v
Database
```

Together, metrics, logs, and traces provide a much more complete view of system health.

---

# 14. Monitoring vs Observability

## Monitoring

Monitoring focuses on known conditions and predefined metrics.

Example:

> Alert me when EC2 CPU utilization goes above 80%.

## Observability

Observability goes deeper and helps understand why a system behaves in a particular way.

Example:

> The application is slow. Which service, dependency, database query, or request path is responsible?

Therefore:

**Monitoring tells us that something is wrong.**

**Observability helps us understand why it is wrong.**

A typical AWS observability architecture can look like:

```text

                         |
          +--------------+--------------+
          |              |              |
       Metrics          Logs          Traces
          |              |              |
          v              v              v
   Prometheus /       CloudWatch       X-Ray
   CloudWatch           Logs
          \              |              /
           \             |             /
            +------------+------------+
                         |
                         v
                Visualization
                         |
              +----------+----------+
              |                     |
           Grafana              OpenSearch
```

OpenTelemetry/ADOT can also be used as a common telemetry collection layer.

# 18. Conclusion

AWS provides a complete observability ecosystem for monitoring infrastructure, applications, users, and distributed systems.

For a DevOps engineer, understanding observability is important because it helps with:

* Faster troubleshooting
* Proactive monitoring
* Performance optimization
* Incident investigation
* Application reliability
* Security and auditing

The most important concept learned from this task is that observability is not just about checking whether a server is running. It is about collecting and correlating metrics, logs, traces, and events to understand the complete behavior of a system.
