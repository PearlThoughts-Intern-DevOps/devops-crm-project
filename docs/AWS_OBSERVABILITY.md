# AWS Observability

## 1. Introduction

AWS Observability is the practice of monitoring, collecting, analyzing, and understanding the behavior and health of applications, infrastructure, and AWS resources.

Observability helps DevOps teams answer important questions such as:

* Is the application healthy?
* Is the infrastructure performing normally?
* Why is an application slow?
* Which service is causing an error?
* When did an issue start?
* What changed before the issue occurred?
* Which users or services are affected?

AWS provides multiple observability services that work together to collect and analyze **metrics, logs, traces, events, and audit information**.

---

# 2. What is Observability?

Observability is the ability to understand the internal state of a system by examining the data it produces.

The three major pillars of observability are:

### 2.1 Metrics

Metrics are numerical measurements collected over time.

Examples:

* EC2 CPU utilization
* Memory utilization
* Network traffic
* Request count
* Error rate
* Response latency
* Database connections

Metrics are useful for identifying trends and creating alarms.

### 2.2 Logs

Logs are records of events generated by applications, operating systems, and AWS services.

Examples:

```text
Application started successfully
User authentication failed
Database connection timeout
HTTP 500 error
```

Logs provide detailed information about what happened inside a system.

### 2.3 Traces

Traces follow a request as it travels through multiple services.

For example:

```text
User
  |
  v
Load Balancer
  |
  v
Application
  |
  v
Database
```

Tracing helps identify which part of the request path is causing latency or failure.

# 3. Major AWS Observability Services

## 3.1 Amazon CloudWatch

Amazon CloudWatch is the primary AWS monitoring and observability service.

It can collect and monitor:

* Metrics
* Logs
* Events
* Application telemetry
* Infrastructure information

CloudWatch can be used to monitor services such as:

* Amazon EC2
* Amazon RDS
* Amazon ECS
* Amazon EKS
* AWS Lambda
* Application Load Balancer
* Amazon S3
* Other AWS resources

### Main uses

* Monitor infrastructure
* Collect logs
* Create dashboards
* Create alarms
* Analyze application performance
* Detect operational problems
* Monitor AWS resources

CloudWatch acts as a central monitoring platform for many AWS workloads.

---

# 4. CloudWatch Metrics

CloudWatch Metrics are numerical measurements used to monitor system and application performance.

Examples include:

| Resource | Example Metrics                       |
| -------- | ------------------------------------- |
| EC2      | CPUUtilization, NetworkIn, NetworkOut |
| RDS      | CPUUtilization, DatabaseConnections   |
| ALB      | RequestCount, TargetResponseTime      |
| Lambda   | Invocations, Errors, Duration         |
| S3       | BucketSizeBytes, NumberOfObjects      |

Metrics can be displayed using graphs and dashboards.

### Example

If an EC2 instance normally operates at 30% CPU but suddenly reaches 95%, the metric can indicate a potential performance problem.

---

# 5. CloudWatch Logs

CloudWatch Logs provides centralized collection and storage of log data.

Applications and infrastructure can send logs to CloudWatch Logs for analysis.

Common sources include:

* EC2 instances
* Lambda functions
* ECS workloads
* Applications
* CloudWatch agents

Logs are organized using:

```text
Log Group
    |
    +-- Log Stream
    |
    +-- Log Stream
```

### Log Group

A Log Group is a collection of related log streams.

### Log Stream

A Log Stream represents a sequence of log events from a particular source.

### Uses

CloudWatch Logs can be used to:

* Troubleshoot applications
* Search errors
* Investigate incidents
* Monitor application behavior
* Store application logs centrally

---

# 6. CloudWatch Logs Insights

CloudWatch Logs Insights allows users to interactively query and analyze log data.

Instead of manually searching through large log files, queries can be used to find specific events.

Example:

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

This can help identify recent error messages quickly.

### Benefits

* Faster troubleshooting
* Search large amounts of logs
* Filter errors
* Analyze application behavior
* Identify patterns

---

# 7. CloudWatch Alarms

CloudWatch Alarms monitor metrics and take action when defined conditions are met.

For example:

```text
CPU Utilization > 80%
        |
        v
CloudWatch Alarm
        |
        v
Notification / Action
```

An alarm can be configured with:

* Threshold
* Evaluation period
* Metric
* Comparison condition
* Alarm actions

### Example

If:

```text
CPU Utilization > 80%
```

for a specified period, CloudWatch can trigger an alarm and send a notification through Amazon SNS or initiate another supported action.

### Use cases

* High CPU alerts
* High error-rate alerts
* Database connection alerts
* Application latency alerts
* Infrastructure health monitoring

# 9. CloudWatch Application Signals

CloudWatch Application Signals provides application-centric observability.

It helps monitor:

* Availability
* Latency
* Faults
* Errors
* Call volume
* Service dependencies
* Service-level objectives

Application Signals can automatically discover application services and dependencies in supported environments and provide service health information.

It can integrate with AWS Distro for OpenTelemetry (ADOT) and the CloudWatch agent to collect application metrics and traces.

### Benefits

* Application performance monitoring
* Service dependency visibility
* Faster troubleshooting
* Service health monitoring
* SLI/SLO-oriented monitoring

Application Signals can be used with environments including Amazon EC2, Amazon ECS, and Amazon EKS.

# 10. AWS X-Ray

AWS X-Ray is a distributed tracing service used to analyze requests across applications and services.

For example:

```text
Client
  |
  v
Load Balancer
  |
  v
Application
  |
  +------> Service A
  |
  +------> Service B
              |
              v
           Database
```

X-Ray helps identify:

* Slow requests
* Application errors
* Service dependencies
* Latency
* Bottlenecks
* Failed downstream services

X-Ray can provide a visual trace map showing how requests move through an application.

AWS recommends moving toward OpenTelemetry for new instrumentation; the X-Ray SDKs and daemon entered maintenance mode in February 2026.

---

# 11. AWS CloudTrail

AWS CloudTrail records actions taken in an AWS account.

It is primarily used for:

* Auditing
* Security monitoring
* Governance
* Compliance
* Investigating account activity

CloudTrail records API activity such as actions performed through:

* AWS Management Console
* AWS CLI
* AWS SDKs
* AWS services

### Example

If someone modifies an EC2 security group, CloudTrail can provide information about the API activity associated with that change.

CloudTrail helps answer:

```text
Who performed the action?
What action was performed?
When was it performed?
Which resource was affected?
Where did the request originate?
```

CloudTrail is therefore different from CloudWatch:

| CloudWatch                   | CloudTrail              |
| ---------------------------- | ----------------------- |
| Monitoring and observability | Auditing and governance |
| Metrics                      | API activity            |
| Logs                         | API/event history       |
| Alarms                       | Security investigation  |
| Performance monitoring       | Who did what and when   |

CloudTrail and CloudWatch complement each other.

# 12. AWS Config

It can track configuration changes to AWS resources and help determine whether resources comply with defined rules.

### Example

An organization may require:

```text

```

AWS Config can help evaluate the configuration against such requirements.

### Uses

* Configuration tracking
* Compliance monitoring
* Security auditing
* Resource inventory
* Change history

# 13. AWS Health Dashboard

AWS Health Dashboard provides information about AWS service events that may affect AWS resources or accounts.

It can provide information about:

* AWS service issues

This is useful when an application appears unhealthy and the problem may be related to an AWS service rather than the application's own configuration.

# 16. AWS Distro for OpenTelemetry (ADOT)

AWS Distro for OpenTelemetry is an AWS-supported distribution of OpenTelemetry.

OpenTelemetry is an open-source observability framework for generating, collecting, and exporting telemetry.

It supports telemetry such as:

* Metrics
* Traces
* Logs

ADOT can be used with CloudWatch and X-Ray-related observability workflows.

AWS documentation describes the CloudWatch agent as an integrated OpenTelemetry Collector option, while upstream or custom OpenTelemetry collectors can also be used depending on the architecture.

### Benefits

* OpenTelemetry compatibility
* Standardized telemetry
* Vendor flexibility
* Application instrumentation
* Metrics and traces collection

# 20. Observability: Metrics vs Logs vs Traces

| Type       | What it tells us        | Example                    |
| ---------- | ----------------------- | -------------------------- |
| Metrics    | What is happening       | CPU = 90%                  |
| Logs       | What happened           | Database connection failed |
| Traces     | Where the request went  | API → Service → DB         |
| Events     | What changed            | Security group modified    |
| Audit logs | Who performed an action | IAM user changed resource  |

These sources complement each other.

### Example troubleshooting scenario

Suppose an application becomes slow.

**Step 1 – Metrics**

CloudWatch shows:

```text
CPU = 95%
Latency = 2 seconds
```

**Step 2 – Logs**

CloudWatch Logs shows:

```text
Database connection timeout
```

**Step 3 – Traces**

X-Ray or OpenTelemetry tracing shows that most request time is being spent waiting for the database.

**Step 4 – Audit**

CloudTrail can be checked to determine whether an AWS configuration change occurred before the issue.

This combination provides much better visibility than using only one monitoring source.

# 23. Importance of Observability in DevOps

Observability is important because modern applications can contain multiple components and dependencies.

Without observability, troubleshooting often becomes:

```text
Problem
   |
   v
Manual investigation
   |
   v
Check server
   |
   v
Check application
   |
   v
Check database
   |
   v
Find root cause
```

With proper observability:

```text
Problem
   |
   v
Metrics / Logs / Traces
   |
   v
Identify affected service
   |
   v
Investigate root cause
   |
   v
Resolve issue
```

This can reduce troubleshooting time and improve system reliability.

# 24. Security and Observability Best Practices

The following practices should be followed:

### 1. Use least-privilege IAM

Give monitoring services and users only the permissions they require.

### 2. Protect sensitive logs

Do not unnecessarily store:

* Passwords
* Access keys
* Tokens
* Sensitive personal information

in application logs.

### 3. Set useful alarms

Avoid creating too many alarms that generate unnecessary notifications.

### 4. Centralize logs

Centralized logging makes troubleshooting easier.

### 5. Use dashboards

Create dashboards for important production metrics.

### 6. Monitor trends

Don't only investigate failures. Monitor trends such as:

* Increasing latency
* Increasing error rate
* Increasing CPU usage
* Increasing traffic

### 7. Use retention policies

Configure appropriate log retention based on operational, security, and compliance requirements.

### 8. Use encryption

Protect observability data using appropriate AWS encryption mechanisms.

### 9. Correlate telemetry

Use metrics, logs, and traces together to investigate incidents.

### 10. Monitor costs

Observability generates data and can incur costs. Review log volume, metric usage, tracing, and retention regularly.
