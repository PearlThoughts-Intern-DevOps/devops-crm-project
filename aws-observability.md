My Learning on AWS Observability

Introduction

During my learning of AWS Observability, I explored how observability helps me understand what is happening inside cloud applications and infrastructure. I learned that monitoring and observability are related concepts, but they serve different purposes. Monitoring mainly helps me track known conditions and identify whether systems are working as expected, while observability gives me deeper insight into the internal state and behavior of a system. I understood that observability is especially useful when I need to investigate unexpected problems or understand why something is failing.

What I Learned About Observability

I learned that the main sources of observability are metrics, logs, and traces. Metrics helped me understand system performance through measurable values such as CPU utilization, memory usage, request counts, and latency. Logs helped me examine detailed records of events and activities within applications and infrastructure. Traces helped me follow requests as they move through different services, making it easier for me to identify where delays or failures occur.

I also explored the major AWS services used for observability. I learned how Amazon CloudWatch can be used to collect metrics and logs, create dashboards, configure alarms, and monitor applications and infrastructure. I understood that CloudWatch can help me detect unusual behavior and respond to issues before they become larger problems.

I explored AWS X-Ray and learned how distributed application requests can be traced across different components. This helped me understand how tracing can be useful for identifying performance bottlenecks and failures in applications that use multiple services.

I also studied AWS CloudTrail, which helped me understand auditing and tracking API activity. I learned that CloudTrail can show who performed an action, what action was performed, and when it occurred. This makes it useful for security investigations, compliance, and troubleshooting configuration changes.

Another service I explored was AWS Config. I learned how it helps track resource configurations and changes over time. I understood that this is valuable when I need to identify configuration problems or verify whether resources follow expected rules.

I also explored Amazon Managed Service for Prometheus and Amazon Managed Grafana. I learned that Prometheus is useful for collecting and querying time-series metrics, while Grafana helps me visualize data through dashboards. Together, they can provide a clear view of application and infrastructure performance.

Practical Understanding

Through these topics, I learned how different observability tools support different real-world situations. I understood that logs can help me investigate application errors, metrics can help me monitor performance, traces can help me troubleshoot distributed applications, alarms can notify me when specific thresholds or conditions are reached, and dashboards can give me a centralized view of system health.

I also learned that observability is useful for troubleshooting, performance monitoring, auditing, and anomaly detection. Instead of relying on a single source of information, I understood how combining metrics, logs, and traces gives me better context and helps me investigate issues more effectively.

Overall Learning

Overall, I learned that AWS Observability is an important part of managing cloud environments and supporting DevOps practices. I understood how different AWS services work together to provide visibility into infrastructure and applications. Most importantly, I learned how observability helps me detect issues, analyze their causes, troubleshoot problems, monitor performance, and support faster resolution. This learning gave me a clearer understanding of how DevOps teams can use AWS observability tools to maintain reliable, performant, and well-monitored cloud applications.
